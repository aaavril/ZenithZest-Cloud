Infraestructura como código

Terraform: las bases que aplicamos

State remoto con lock

Bucket de Cloud Storage versionado, con bloqueo nativo; un state por entorno.

Versiones fijadas

Terraform 1.9.8, provider ~> 6.0 y el lock file versionado en Git.

Etiquetas obligatorias

project · team · env · owner en todos los recursos, desde el provider.

Variables validadas

Tipo, descripción y validación en todas; rechaza un ID inválido o una imagen latest.

Imagen por SHA

Nunca latest: cada despliegue usa el commit exacto, y volver atrás es volver al commit anterior.

Destroy limpio

Un clic en destroy.yml y la evidencia de que el state quedó vacío.

ZenithZest · Cloud Computing UCU

Avril (4:45–5:15). Introducción a Terraform antes de mostrar cómo lo armamos. Terraform es declarativo: describimos cómo queremos que quede la infraestructura y la herramienta calcula qué crear, cambiar o borrar (el plan). Lo recuerda en el state, que va a un bucket privado con bloqueo para que dos procesos no apliquen cambios a la vez, y nunca a Git porque puede tener secretos. Encima de eso, las bases: versiones fijadas, etiquetas en todo, variables validadas, imágenes por SHA y un destroy limpio.
